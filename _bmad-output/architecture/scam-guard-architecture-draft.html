Architecture Draft · Scam-Guard · v0.1 (naive) · 2026-09-29

System sketch — every component discussed so far, wired together once

Not an engineering spec. This is the first pass at turning the dossier's decisions (tier ladder, response model, confirmation policy, business-model integrations) into boxes and arrows, so the next design pass has a shape to argue with instead of a blank page.

Naive on purpose: no scaling numbers, no exact APIs/schemas, no deployment topology. Just: what are the parts, what does each own, and what talks to what.

Component map

Three zones: client (runs on the person's device), core cloud (Scam-Guard's own backend), external (standards and partners it plugs into, never rebuilds).

Known gaps in this draft

Named so the next pass doesn't quietly assume these are solved.

Message/SMS content classification has no mature open-source component to slot in — flagged in the dossier as the one build-it-yourself layer. Not represented as a real box above; it's a gap inside "Sentinel Agent," not a solved collector.
No data model or storage layer drawn — what the Correlation Service and Confirmation Engine actually persist, retention, and encryption-at-rest are all undesigned.
No auth/tenancy model for the Partner Integration Layer — how a bank's fraud desk authenticates and what it's scoped to see is unspecified.
Confirmation Engine's exact thresholds are still qualitative ("a few reports" / "many, trust-weighted") — no concrete numbers chosen yet.
Offline/degraded-connectivity behavior for the Sentinel Agent isn't addressed — Free tier's "no cloud dependency for the core promise" implies local-only fallback, not yet designed.
